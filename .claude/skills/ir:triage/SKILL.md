# Triage and Plan Irrlicht Issues

Prepare an issue for `/ir:exec`. Diagnose the issue and make the design,
testing, and process choices that execution needs. Do not implement the fix.
Pass `--repo ingo-eichhorst/Irrlicht` to every `gh` command.

## Invocation

- `/ir:triage` — process every open issue without a state label.
- `/ir:triage #278` — process one issue.
- `/ir:triage #278 #277` — process several issues.

For a sweep, enumerate issues with no state role:

```bash
gh issue list --repo ingo-eichhorst/Irrlicht --state open --limit 200 \
  --json number,labels --jq '.[] | select(
    [.labels[].name] | any(. == "needs-triage" or . == "needs-info" or
      . == "ready-for-agent" or . == "ready-for-human" or . == "wontfix") | not
  ) | .number'
```

Process issues one at a time. Skip an already-triaged issue during a sweep.
Always re-triage an explicitly named issue. Edit the prior AI triage comment
instead of appending another one.

Start every comment with:

```text
> *This was generated by AI during triage.*
```

## Workflow

1. Read the issue and all comments.
2. Inspect the cited code, nearby tests, architecture boundaries, and applicable frontends. Do not run tests or change files.
3. Check readiness and hard blockers.
4. Choose one high-level design and one testing strategy.
5. Set complexity, process, estimate, labels, and milestone.
6. Post the assessment and apply metadata in one issue edit.

Treat a dismissal such as “already fixed,” “self-heals,” or “not relevant” as
an assumption until code, a command, or a cited PR verifies it. Mark an
unchecked dismissal as assumed. Do not use it to reduce scope or risk.

## Readiness

Score each axis with `✓` or `✗` and one evidence-based sentence.

| Axis | Pass condition |
|---|---|
| Scope | The affected behavior and likely components are bounded. |
| Specification | No external or hard-to-reverse decision remains. |
| Verifiability | A concrete signal can distinguish success from failure. |
| Observability | Existing or small new instrumentation can expose that signal. |
| Context | Relevant code and prior work are cited or directly findable. |
| Independence | No unresolved issue, PR, credential, or human decision blocks work. |
| Reversibility | The change is local and can be reverted safely. |

Any failure except low- or medium-cost Observability gives `needs-info`.
Default to `ready-for-agent` when the issue is bounded and reversible. Do not
block on a reversible implementation choice. Choose that choice in the design.

Use these Observability costs:

- **Low:** Run an existing recording, replay, CLI, metric, or snapshot tool.
- **Medium:** Extend an existing event, metric, fixture, or snapshot surface.
- **High:** Build a new observation system. Use `needs-info` and name the
  prerequisite. Do not open a new issue without maintainer approval.

For a Low or Medium gap, put the required instrument first in the testing
strategy.

For a pasted test without a shown failure on `main`, pass Verifiability when
the criterion is concrete but mark it **unproven**. Mark behavior-preserving
tests as **locks**.

Use `wontfix` only for a verified duplicate, invalid report, or out-of-scope
request. Post one evidence-based paragraph and close it.

## High-level design

For each `ready-for-agent` issue, write a short list that fixes:

- the intended behavior and component boundaries;
- the data or control flow;
- the applicable macOS and web surfaces;
- compatibility, permission, and persistence constraints;
- explicit exclusions.

Use existing repository patterns. Choose one direction. Do not list alternative
designs. The design is a strong default for execution, not a file-by-file plan.

## Testing strategy

Write a short list. Name exact test targets, fixtures, commands, UI
checks, or observable outputs. Classify each relevant proof:

- **red-first:** a defect test must fail before the fix;
- **lock:** a behavior-preserving test passes before and after;
- **mutation:** a new guard, rule, migration, rewriter, or contract check must
  fail when its protected condition is deliberately broken;
- **manual:** a physical or UI check that a person must perform.

Do not claim that an unrun test proves a defect. Mark it **unproven**.

## Complexity and process

Set a base level from expected touch points. Add one level for one material
design uncertainty or two levels for several. Cap the result at 10.

| Level | Expected change |
|---|---|
| 1–2 | One file or one unambiguous local fix. |
| 3–4 | One function or a small two-file extension. |
| 5–6 | One established slice across two to four files. |
| 7–8 | Cross-cutting, schema, architecture-boundary, or frontend-parity work. |
| 9–10 | A subsystem or multi-phase change. |

Level 9–10, an unbounded issue, or level 7–8 without a phase boundary gives
`needs-info`. Ask the reporter or maintainer to split or bound it. Do not invent
child issues.

Set the initial execution process from the effective level:

| Level | Investigation | Review | Simplify |
|---|---|---|---|
| 1–2 | direct read | low | inline |
| 3–4 | 1 Explore, medium | low | inline |
| 5–6 | 1–2 Explore, medium | medium | `/simplify` |
| 7–8 | 2–3 Explore, thorough | high | `/simplify` |

`ir:exec` can recalibrate review effort in either direction after it measures
the real diff. It must record the reason. Investigation and simplify values
come from this table.

## Estimate

Report agent-active time and human gates separately:

| Level | Agent-active time |
|---|---|
| 1–2 | 15–45 min |
| 3–4 | 45 min–2 h |
| 5–6 | 1.5–3 h |
| 7–8 | 2.5–5 h |

Change a range only for a named, observed driver. List each gate and its owner.
Examples are a credential, a physical action, or manual visual acceptance. A
gate does not change readiness unless it is a real prerequisite.

## Labels and milestone

Apply one category:

- `bug` for broken behavior or a regression;
- `enhancement` for new behavior, refactoring, or polish.

Apply one state: `ready-for-agent`, `needs-info`, or `wontfix`.

Apply priority to ready issues:

- `Priority-High` for a blocker or user-visible regression;
- `Priority-Medium` for important non-blocking work;
- `Priority-Low` for optional polish.

Add `scope:<directory-name>` for a clear adapter, platform, or module owner.
Use multiple scopes for cross-cutting work. Common non-directory aliases are
`scope:daemon`, `scope:cli`, `scope:replay`, `scope:tooling`, and `scope:site`.

Apply flags only with a specific reason:

- `good first issue`: level 1–2, local, and no specialized or unsafe code;
- `help wanted`: ready but outside the near-term maintainer plan;
- `documentation`: only documentation changes;
- `adapter-request`: support for a new coding agent;
- `track:brand`: UI, marketing, or overlay design;
- `duplicate` or `invalid`: verified dismissal only.

Keep an existing maintainer-set milestone. Otherwise derive release buckets
from the repository `version.json`:

```bash
DEV_MM=$(jq -r .version "$(git rev-parse --show-toplevel)/version.json" |
  sed -E 's/^v//; s/^([0-9]+\.[0-9]+).*/\1/')
ACTIVE="v$DEV_MM"
NEXT="v$(awk -v v="$DEV_MM" 'BEGIN{split(v,a,"."); print a[1]"."a[2]+1}')"
FUTURE="v$(awk -v v="$DEV_MM" 'BEGIN{split(v,a,"."); print a[1]"."a[2]+2}')"
```

Map High to `$ACTIVE`, Medium to `$NEXT`, and Low to `$FUTURE`. Create a
missing open milestone once per run. If `version.json` is invalid, omit the
milestone and report the failure. Do not fall back to release tags.

## Assessment format

Use this compact template. Omit fields marked as optional when empty.

```markdown
> *This was generated by AI during triage.*

## Triage Assessment

**Category:** <bug | enhancement> — <reason>
**Priority:** <High | Medium | Low> — <reason; ready only>
**Scope:** <labels> — <reason; optional>
**Flags:** <labels> — <reason; optional>
**Milestone:** <vMAJ.MIN> — <reason; ready only>
**Complexity:** <effective> (base <n>, uncertainty +<n>) — <reason>
**Process:** investigation <direct | 1 Explore | 1–2 Explore | 2–3 Explore> · review <low | medium | high> · simplify <inline | /simplify>
**Estimate:** <range> agent-active · gates: <none | gate and owner> — <driver>

**Readiness:**
- ✓/✗ **Scope** — <reason>
- ✓/✗ **Specification** — <reason>
- ✓/✗ **Verifiability** — <reason>
- ✓/✗ **Observability** — <reason and cost when failed>
- ✓/✗ **Context** — <reason>
- ✓/✗ **Independence** — <reason>
- ✓/✗ **Reversibility** — <reason>

## High-level design

- <chosen design point>

## Testing strategy

- <classification: exact proof and command>

**Verdict:** ready-for-agent | needs-info

<!-- needs-info only -->
**Blocked on:**
- <one specific action and owner>
```

For `needs-info`, omit Priority, Milestone, Process, Estimate, design, and test
strategy when a blocker prevents those choices from being valid.

Apply labels and a milestone in one call:

```bash
gh issue edit <N> --repo ingo-eichhorst/Irrlicht \
  --add-label <category>,<state>[,<Priority-X>][,<scope-or-flag>...] \
  --remove-label <obsolete-state-labels> \
  --milestone "<vMAJ.MIN>"
```

Omit `--milestone` for `needs-info`, `wontfix`, or an existing maintainer-set
milestone. Never remove the state that this run adds. Create a missing scope
label or milestone before this call. Justify every applied label.
