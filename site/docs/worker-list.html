Worker List

Show any pool of agents in Irrlicht by writing one JSON status file.

When to use it

Irrlicht finds most agents by itself, from the transcripts and processes on the machine it runs on. Some setups hide exactly that: agents in containers or micro-VMs, CI runner fleets, a home-grown scheduler that hands work to slots. What such a setup does know is which workers exist, whether each one is busy, what it works on, and whether it is alive. The worker list is how it tells Irrlicht.

A program you run (the writer, typically your scheduler or supervisor) keeps one JSON file up to date. Irrlicht reads it and shows one group per pool, one sub-group per team, and one row per worker: busy or free, its work item, a stale tag when it stops reporting, a failed tag after a failed run, and a waiting row with a notification when its agent waits for a person. No transcript, prompt or output ever needs to reach Irrlicht.

Where the file goes

  • Path. workerlist.json in Irrlicht's data directory: ~/.local/share/irrlicht (also on macOS), or $IRRLICHT_HOME when it is set.
  • Override. IRRLICHT_WORKERLIST_FILE points the daemon at another path. A daemon started by Irrlicht.app sees only the app's environment, which normally does not include your shell profile, so the default path is the one that needs no setup. See Configuration.
  • Consent. Grant Worker list in Irrlicht's permissions. Nothing is read before that, and revoking it removes the group at once.
  • Writing. Replace the file atomically: write a temporary file next to it, then rename it over workerlist.json. The daemon watches the directory and also re-reads the file every 30 seconds, so a pool whose writer died still turns stale.

Schema v1

{
  "schema": 1,
  "name": "VM tasks",
  "heartbeat_interval_seconds": 60,
  "teams": [{
    "name": "lead-T100",
    "updated": "2026-11-21T15:40:00Z",
    "workers": [
      {"name": "T101", "busy": true, "work_item": "T101",
       "last_heartbeat": "2026-11-21T15:39:30Z"},
      {"name": "T102", "busy": true, "state": "waiting", "work_item": "T102",
       "last_heartbeat": "2026-11-21T15:39:30Z"},
      {"name": "T103", "busy": false,
       "last_run": {"end": "2026-11-21T14:52:00Z", "exit": 1}}
    ]
  }]
}

Document

Field Type Description
schema integer, required Must be 1.
name string The group header. Default: “Worker pool”.
heartbeat_interval_seconds integer How often your writer reports. Above 0; default 60. A worker or team is stale after three intervals without a report.
teams array, required One entry per team. Team names must be unique in the file.

Team

Field Type Description
name string, required The sub-group header.
updated RFC 3339, required Stamped by the team's own writer on every write. If you merge several teams into one file, copy each team's updated unchanged; restamping it would hide a team whose scheduler died.
workers array, required One entry per worker. Worker names must be unique within the team.

Worker

Field Type Description
name string, required The worker's row label.
busy boolean, required true while the worker holds work.
state string Only "waiting", and only on a busy worker: its agent waits for a person. Omit it otherwise.
work_item string What the worker works on. Rows show the first 8 characters, the full value in the tooltip.
last_heartbeat RFC 3339 The worker's last sign of life.
last_run object {"end": RFC 3339, "exit": integer or null}, the worker's last completed run.

Unknown fields are accepted and ignored, so your own bookkeeping can stay in the file. So are a top-level updated, a team's last_tick, and a worker's activity, last_run.start and last_run.note.

What Irrlicht shows

  • Busy and free. Each worker row shows its name, its work item and busy or idle. A team with only free workers stays visible.
  • Stale. A busy worker is stale when its last_heartbeat is older than three heartbeat intervals (180 seconds at the default 60). A busy worker without a heartbeat falls back to its team's updated. A team whose updated is that old shows stale in its header, and so do all its busy workers. A free worker is never stale.
  • Failed. A last_run with an end and a non-zero exit shows a failed · exit N tag on the row. It sends no notification.
  • Waiting. A worker with "state": "waiting" is painted in the waiting colour with a filled dot. When a worker Irrlicht has already seen turns waiting, the macOS app and the web dashboard send Worker waiting for input, under the same notification setting as a waiting session. A worker first seen already waiting, after a restart for example, does not notify. The daemon tells the macOS app as soon as a worker's state changes; the web dashboard re-checks every 2.5 seconds while a pool is listed.
  • Unreadable. A file that does not parse, misses a required field, repeats a name, uses another schema or another state value, or marks a free worker ("busy": false) as "waiting" is refused as a whole. Irrlicht keeps showing the last good file with every team marked unreadable, and logs the reason. With no file at all there is no group.
  • Lifetime. A worker is shown exactly as long as it is in the file. Drop finished work from the file when it should disappear.

Relayed sessions. When a worker runs its own Irrlicht daemon and forwards through irrlichtrelay, a forwarded session whose daemon label equals the worker's name is shown in that worker's row, with its live state, tokens and cost. That session then notifies for itself, so the worker's own waiting sends no second notification. The worker list does not need any of this: a worker that sends nothing but this file is still listed.

Example: agents in isolated VMs

One coding agent runs per task in its own VM or container, and a lead task hands work to several of them. Only results leave the VM. A host-side supervisor knows each task's id, its lead, and its lifecycle, and writes:

  • each lead task as a team, and each task as a worker in it;
  • a running task as "busy": true with a fresh last_heartbeat;
  • a task whose agent asks a question as "busy": true, "state": "waiting";
  • a finished task as "busy": false with its last_run, until the supervisor drops it.

The supervisor learns that an agent waits from a signal that carries no content, for example an agent hook inside the VM that writes the single word waiting to a file the host can read.
